# RUDER-AI

**言語:** [English](README.md) · [한국어](README.ko.md) · **[日本語](README.ja.md)** · [简体中文](README.zh.md)

**RUDER-AI** は、自然言語で依頼されたタスクをソフトウェアワークスペース内における
実在の検証可能な変更へと変える、ロール分離型の自律コーディングエージェントです。

RUDER-AI は LLM の推論と決定論的 Tool 実行、ロール単位の権限付与、独立した検証、
多言語モデル設定を組み合わせています。

## 必要条件

* Python 3.10 以降
* ローカルで稼働中の [Ollama](https://ollama.com)（既定値は `http://127.0.0.1:11434`）
* `tkinter` — Windows/macOS の CPython には同梱されています。Linux で GUI が
  必要な場合は `python3-tk` をインストールしてください。ターミナルエージェントと
  テストスイートは使用しません。

## インストール

```bash
git clone https://github.com/Mintsirup/ruder-ai.git
cd ruder-ai
python -m pip install -e .
```

この操作で `ruder-ai` CLI がインストールされます。対話型エージェントは次のように
起動します。

```bash
ruder-ai start --dir /path/to/your/project --model ruder-ai-ko
```

### コマンド

| コマンド | 動作 |
|---|---|
| `ruder-ai start` | 対象プロジェクトで対話型エージェントを実行 |
| `ruder-ai gui` | デスクトップエディタ + AI コンソールを起動 |
| `ruder-ai where` | 実際に実行されているチェックアウトを表示し、別の複製に差分があれば警告 |
| `ruder-ai survey` | プロジェクトの全ファイルをロール別に分類して説明（LLM 呼び出しなし） |
| `ruder-ai bench` | 主要区間を計測: scan, index, plan, context, 編集反映 |
| `ruder-ai config` | 設定ウィンドウを開く |

## デスクトップ GUI

RuderAI Studio は Code-OSS 形式のデスクトップアプリです — ファイルエクスプローラ、
マルチタブエディタ、AI コンソール、内蔵ターミナルを、Python 標準ライブラリの
`tkinter` だけで実装しています。インストールする GUI バイナリは存在しないため、
`pip install -e .` 以外に追加で必要になるものはありません。

```bash
ruder-ai gui      # RuderAI Studio を起動
ruder-ai config   # 設定ウィンドウ: ワークスペース、Ollama URL、モデル、temperature
```

注意点:

* すべての実行 — CLI、GUI チャット、`.ruder_ai_logs/` の JSONL 実行ログ — は明示的な
  `End Of Token` マーカーで終端されるため、会話ログは常に「エージェントが終了した」
  と「ストリームが途中で切れた」を区別できます。ログ上では `end_of_token` イベントです。
* 子プロセスから取得した出力（`execute_code`、`execute_shell`、`git`、検証ランナー）は
  子側で UTF-8 に強制されます。Windows ではパイプされたプロセスは stdout を ANSI
  コードページでエンコードするため、これがないとエージェントが 자신이直前に書いた
  韓国語の出力を mojibake として読み、自分の書いたコードが壊れたと結論づけてしまいます。
* `tkinter` は Windows と macOS の CPython に同梱されています。一部の軽量 Linux
  イメージには `python3-tk` が必要です。ヘッドレス環境（サーバー、Termux）には
  ディスプレイがないため GUI は実行できません — その場合は `ruder-ai start` を使ってください。
* 内蔵ターミナルは**実際の TTY**に接続されます: Linux/macOS では PTY、Windows では
  Win32 **ConPTY** 擬似コンソールを使うため、`vim`、`htop`、言語 REPL が正常に動作します。
  ホストが ConPTY API を公開していてもコンソールホストの割り当てを拒否する場合
  （コンテナ、非対話セッション、一部 CI ランナー）、Studio はパイプシェルに縮退し、
  その事実をターミナルに通知します — 通常のコマンドは引き続き動作しますが、
  フルスクリーンプログラムは動作しません。
* `gui` と `config` はターミナルエージェントと同じ `.ruder_ai_config.json` を
  読み書きするため、モデルやホストの変更はすべての場所に適用されます。
* エディタは Python、C 系言語（JS/TS、C#、Java、C/C++、Go、Rust、Kotlin、Swift、PHP、
  Lua）、JSON、YAML、シェル、CSS、マークダウン、XML/HTML、Ruby に対して構文
  ハイライトに対応します。ハイライトはデバウンスされ、非常に大きいバッファや
  異常に長い行の場合は、停止させる代わりにハイライトなしで描画します。
* 検索/置換: `Ctrl+F` / `Ctrl+H`、繰り返しは `F3` と `Shift+F3`、パネルを閉じるか
  選択を解除するには `Esc`。オプションは大文字小文字の区別、単語全体、正規表現、
  そして完全一致が得られない場合に近傍候補を提示する「오타 허용」フォールバックです。
  不正なパターンは例外を投げずに報告され、ステータス行に `Ln/Col` が表示されます。
* 単語全体の一致は正規表現の `\b` ではなく Unicode を考慮した方式で動作するため、
  韓国語/CJK や `//` のような記号からなる検索文字列でも正しく機能します。正規表現
  検索は複数行にまたがるため、`^import` は `import` で始まるすべての行に一致します。

## 開発

テストスイートはリポジトリルートで実行します:

```bash
python -m pip install pytest pytest-asyncio
python -m pytest
```

`tests/conftest.py` は既定で `RUDER_AI_BENCHMARK_FIXTURE_MODE` を有効にします。
これは実際のモデルを呼び出す代わりに、オーケストレーターの決定論的ベンチマーク
回答を選択するモードです。この変数を自分で設定して上書きすることもできます
（例: `RUDER_AI_BENCHMARK_FIXTURE_MODE=0` とするとライブ LLM のコード経路を検証します）。

## 機能

## v7.5.9 エージェントパイプライン

```text
Explorer → Planner → Coder → Tester → Reviewer → Memory
                 \_______________________________/
                           Orchestrator
```

RUDER-AI はコーディングワークフローを専門化された段階に分離します。

### Explorer

読み取り専用のプロジェクト調査。

* プロジェクト構造の確認
* ファイルの検索
* シンボルと参照の点検
* プロジェクトの言語とフレームワークの特定
* ファイルを変更しない

### Planner

実装計画を組み立てます。

* 依頼された作業の分析
* 必要な変更の決定
* 関連ファイルとコンポーネントの特定
* 実装前に構造化された計画を生成

### Coder

計画された変更を適用します。

* ファイルの作成と変更
* パッチの適用
* 許可された開発 Tool の実行
* 計画されたソリューションの実装

検証は意図的に Tester 段階へ延期されます。

### Tester

実装を独立して検証します。

* `verify_project` の実行
* プロジェクト状態の確認
* 実装が実際に機能するかの確認
* ファイルを変更しない

したがって Coder は、自らの作業が成功したかについての最終権限者ではありません。

### Reviewer

現実に対して結果をレビューします。

* 変更されたファイルの確認
* diff の確認
* 実装の主張の検証
* 報告された変更と実際の変更の不一致の特定
* 読み取り専用

### Memory

最終結果を記録します。

* 最終段階の結果を保存
* 重要な決定を記録
* 将来の文脈のためにタスク結果を保持
* Tool アクセスなし

### Orchestrator

パイプライン全体を調整します。

Orchestrator は段階の流れを制御しますが、**Tool 権限を付与しません**。

Tool の認可は、`ruder_ai/agents/permissions.py` の決定論的ロールポリシー
（`ROLE_TOOL_POLICIES`）を用いて `ToolExecutor` が強制します。Executor がすべての
Tool 呼び出しに対して権威ある実行時チェックを行います。

---

## Tool 権限の強制

RUDER-AI はプロンプト上の指示を認可境界として扱いません。

すべての Tool 呼び出しは `ToolExecutor` を通過し、実行前にアクティブなロールを検査します。

```text
Role Agent
    │
    ▼
Tool Call
    │
    ▼
ToolExecutor
    │
    ├── Allowed → Execute Tool
    └── Denied  → permission error
```

ロールエージェントは自分の明示的なロールを Executor に 전달します。

ロールが許可されていない Tool を使用しようとした場合、`ToolExecutor` は決定論的な
`permission` エラーを返します。

### 二重層の保護

Coder はシステムプロンプトを通じて、許可された Tool のみを受け取ります。

しかしプロンプトは最終的なセキュリティ境界とはみなされません。

Executor が実行時に権威ある権限チェックを行います。

```text
LLM Tool visibility
        +
Runtime Tool authorization
        =
Role-enforced Tool access
```

後方互換性のため、`role=None` を使う既存の `ToolExecutor` 直接呼び出しは、
制限なしの従来どおり動作します。

## 検証モデル

RUDER-AI は実装と検証を意図的に分離します。

次のような方式ではなく:

```text
LLM → Modify → "Done"
```

意図されたワークフローは:

```text
Plan
  ↓
Modify
  ↓
Verify
  ↓
Review
  ↓
Record
```

したがって本システムは、Coder の「作業が成功した」という主張だけに依存するのではなく、
独立して観測されたプロジェクト状態を基準に完了を判断しようとします。

## 言語モデル

RUDER-AI は次を基盤으로 언어별モデル設定を提供します:

```text
qwen2.5-coder:7b-instruct
```

現在の設定は次のとおりです:

| モデル         | 言語     | 用途               |
| -------------- | -------- | ------------------ |
| `ruder-ai-ko` | 한국어      | Korean RUDER-AI   |
| `ruder-ai-cn` | 简体中文     | Chinese RUDER-AI  |
| `ruder-ai-en` | English  | English RUDER-AI  |
| `ruder-ai-jp` | 日本語      | Japanese RUDER-AI |

各モデルは同じ RUDER-AI Code Mode アーキテクチャを使いながら、設定された応答言語を
強制します。

技術コード、識別子、クラス名、メソッド名、ソース言語のコメントは、それぞれの言語のまま
維持されます。

自然言語の説明、推論、指示は設定された言語で生成されます。

### モデル設定

`Modelfiles/` の Ollama Modelfile がモデルレベルでサンプリングを設定します:

```text
Temperature: 0.7
Context window: 16384
Base model: qwen2.5-coder:7b-instruct
```

Python ランタイム（`RuderAISettings`）はエージェント実行のために独自の決定論的デフォルトを
使用し、リクエストレベルのサンプリングオプションを上書きします:

```text
Temperature: 0.1
Context window: 16384
Max tokens: 3072
```

したがって実効的なランタイムサンプリングは `RuderAISettings` に従います
（`RUDER_AI_TEMPERATURE` などの環境変数や `ruder-ai config` で設定可能）。Modelfile の
値は、明示的なリクエストオプションなしでモデルが呼び出される場合にのみ適用されます。

これらのモデルの用途:

* RUDER-AI CODE MODE
* `READ_ONLY_INSPECT`

日常的な会話は別に処理され、この Code Mode 設定は経由しません。

## プロジェクト考慮型コーディング

RUDER-AI は特定のプログラミングエコシステムを前提としません。

変更する前に、実際のプロジェクトを調査し次を特定することが期待されます:

* プログラミング言語
* ビルドシステム
* フレームワーク
* プロジェクト構成
* 既存の規約
* 設定およびマニフェストの書式
* 関連する API と依存関係

エージェントは、無関係なアーキテクチャを新たに الأشهر代わりに、プロジェクトに
すでに確立された規約に従うべきです。

次のような設定およびマニフェストファイルについて:

```text
package.json
pom.xml
plugin.yml
Cargo.toml
```

RUDER-AI は対象プロジェクトにすでに確立された規約に従います。

## インデックス性能

インデックス作成はすべてのタスクの前に発生する処理であるため、特に高速化해야する
部分でした。このリポジトリでの計測結果（192 ファイル、1,300 シンボル、Windows、
CPython 3.13）:

| 操作 | 変更前 | 変更後 |
|---|---|---|
| 1 ファイル編集（`refresh_file`） | 302 ms | 3.7 ms |
| 全体インデックスの再構築（warm） | 294 ms | 39 ms |
| `ProjectScanner.scan` | 115 ms | 10 ms |
| `FileResolver.resolve_many` | 114 ms | 5 ms |
| コンテキスト組み立て | 17 ms | 10 ms |
| ファイルシステム署名（リクエストごと） | 9.6 ms | 4 ms |

何を変更し、それぞれがなぜ安全だったか:

* **増分インデックスが実際に機能するようになりました。** `AIAgent.refresh_file` が
  `SymbolIndexer.update_file` を呼んでいましたが、そのメソッドは存在しませんでした。
  すべての「増分」更新が `AttributeError` を発生させ、呼び出し側はそれを握りつぶして
  `project_index = None` を設定していました — つまり 1 ファイルの編集が黙ってワークスペース
  全体の再スキャンと再解析を強制していました。`SymbolIndexer.update_file` と
  `ReferenceIndex.update_file` が存在し、全体再構築とバイト単位で同一の状態に到達します
  （編集、削除、構文エラー、Java ファイルを含めて検証済み）。
* **参照インデックスはシンボル名が移動した場合にのみ再構築されます。** グローバルな
  名前集合を基準とするため、関数本体だけを変更する編集は 1 ファイルに適用でき、
  定義の追加や削除がある場合は全体を再導出します。
* **無視対象のディレクトリは走査中に枝刈りされます。** `node_modules`、`.venv`、
  `build/` などはスキップされ、ルールはワークスペース*内部*のパスに対して照合されます
  — `out` という名前のディレクトリの下にチェックアウト。即使そうしても空のインデックスが
  生成されることはなくなりました。
* **派生データはファイルごとにキャッシュされます。** キーは `(path, size, mtime_ns)` —
  ワークスペース署名が再構築の要否を判断するのに使っていたのと同一の三つ組であるため、
  キャッシュがインデックスより古くなることはありません。全体のビルドは各ファイルを
  3 回ではなく 1 回だけ読み、変更のないファイルはトークン化も再解析も行いません。
* **トークン化とスコアリングは Python レベルの文字単位処理を避けます。** トークン
  推定器の韓国語カウントは C レベルの正規表現 1 回の走査であり、ASCII は高速パスを
  経由します。 CamelCase 分割は分割できないトークンでは省略され、大文字小文字を
  区別しない型参照は事前計算した小文字名を使います。

等価性の証明は `tests/test_v755_performance.py` にあります — AST の走査はリポジトリ内の
すべてのモジュールについて `ast.walk` と比較され、トークナイザは数千の無作為な入力について
前実装と比較され、増分インデクサは全体再構築と比較されます。

同じ数値でいつでも再測定できます:

```bash
ruder-ai bench --dir . --reps 3
```

各段階は計測前にウォームアップされ best-of-N で報告されます。編集反映の計測は
使い捨てのコピー上で実行されるため、あなたの作業ツリーが変更されることはありません。

## ターン意図

挨拶はタスクではありません。`안녕` という一言が planner に到達し、`hello_handler`
モジュールの `write_file` を生み出しました — 誰かが挨拶しただけで、エージェントが
リポジトリを変更してしまいました。planner はすでに取得用の `intent` を計算していましたが、
変更の前にそれを参照する箇所がなく、何も要求されていないターンに対してモデルが
自由に計画を立てられる状態だったのです。

`ruder_ai/core/turn_intent.py` はすべてのターンを 3 種類のいずれかに分類します:

| 種類 | 例 | ファイル変更 |
|---|---|---|
| `CONVERSATIONAL` | `안녕`、`hi`、`thanks!` | 不可 |
| `QUESTION` | `이게 왜 이렇게 짜여 있어?`、`which module handles login?` | 不可 |
| `ACTION` | `auth.py 고쳐줘`、`Add a test for login` | 可 |

この判定は planner ではなく**エグゼキューターで強制**されます。同じモデルが計画を
書きます — 計画を作り出したモデルは、それ自身の言い訳も作り出し得るからです。
`ToolExecutor._check_turn_intent` は `write_file`、`append_file`、`patch_file`、
`delete_file`、`move_file`、`apply_patch` のいずれかを実行する直前に動作し、
変更を許可する表現を明示したうえで `MUTATION_REFUSED_MESSAGE` で拒否します。
読み取り専用の Tool は引き続き利用できます — プロジェクトについての質問はファイル
を開く正当な理由ですが、変更する理由ではありません。

分類器は意図的に拒否側に倒れています。会話用と誤読されたターンのコストは、表現を
表現を明確にした再試行 1 回分のコストにすぎません。実行用と誤読されたターンは、あなたの
コードを静かに編集してしまいます。欧文の挨拶は単語境界で照合されるため、`this`/`which`/`him` が
`hi` として読まれることはありません。

`AIAgent.process_task` は `CONVERSATIONAL` を Tool もインデックスも持たない
LLM 1 回の呼び出しに短絡します。そのため挨拶のコストは「変更されたファイルなし」
という結果を生成する Explorer→Planner→Coder→Tester→Reviewer の全段実行ではなく、
往復 1 回分にすぎません。

## プロジェクトサーベイ

「このプロジェクトを一個ずつ分析して、ファイルごとに機能を一個ずつ説明して」という
依頼が **190 ファイル中 2 ファイル**についてのみ回答し、出力には残りの 188 が
スキップされたことを示す記述が何もありませんでした。問題は二つでした: 190 ファイルを
プロンプトに収める手段が存在しなかったことと、カバレッジが報告されなかったため、

ruder-ai survey --dir .

各ファイルは自身の docstring と AST から説明されます（LLM が推測する内容ではなく、
*何のために*存在するか）。ロール名はディレクトリ、ファイル名、パッケージ構成から
導出されます。以下の出力例では、Tool が出力するラベル（現在、韓国語）がそのまま
表示されます。`covered/total` の行は装飾ではありません: インデックスには存在するが
読み取れないファイルは分母に含まれ、出力に名前が示されるため、この数字が暗黙に
「実際に確認した分」を指すことはありません。

### 一つの答えではなく二つの階層

プロジェクトを*分析*してほしい依頼と、*すべてのファイル*を説明してほしい依頼は
別の依頼であり、両方に 48,000 文字の塊で答えるのは、どちらも答えないのと同じくらい
役に立ちません。両者は別々の経路に分岐します:

| 依頼 | 回答 |
|---|---|
| "모든 프로젝트를 분석해"、"파일마다 기능 일일히 말해줘"、"explain every file" | 全体サーベイ、ファイルごとに 1 セクション |
| "이 프로젝트가 뭐 하는 곳이야?"、"analyze this codebase" | 1 画面分の概要: 規模、トップレベル構成、ロールのヒストグラム、エントリポイント、最大モジュール — さらに全体サーベイに到達する依頼も示します |

どちらも決定論的でモデル呼び出しはありません。どちらでも分析結果は得られますが、
どちらもファイル*変更*に関する質問には答えません — それは以前は読み取り専用の依頼が
回答 先が見つからず、代わりにそこが返されていたのです。

### 壁を読み返さずに続ける

全体サーベイは約 48,000 文字です。チャットペインで二度続けて提供されるのは答えでは
なくスクロールです。そのためサーベイは**一度だけ**配信されます: 同じ依頼には概要と
より絞る方法を示し、全体を明示的に求めたときにのみ再度提供します。名前を明示した
依頼は、その対象だけを受け取ります:

| このように尋ねると | このように答えます |
|---|---|
| `ruder_ai/core/executor.py 는 어떤 일을 해?` | そのファイルの詳細一式 |
| `executor.py 자세히 설명해줘` | basename による同じファイル |
| "테스트 파일만 설명해줘" | 63 個のテストファイルの一覧 |
| "core 디렉터리 자세히" | `core/` 配下の 25 ファイル |
| "없는파일.py 설명해줘" | 概要と誠実な「見つかりません」 |

名前が明示されたファイル、ロール、ディレクトリは概要より優先され、編集の依頼は
その両者より優先されます — `auth.py 고쳐줘` は質問ではなく作業であり、それが変更に
至らないことを保証するのがエグゼキューターのターン意図ゲートです。

韓国語は助詞の正規化後に照合されます。自然言語では助詞が名詞と動詞の間に付きます
— `프로젝트` + `를` + ` ` + `분석해` — そのため助詞を含まないマーカーとの照合は
1 文字ずれて外れ、"모든 프로젝트를 분석해" がルーティング不可能でした。綴りの
変種を列挙するのではなく照合前に助詞を除去します。正規化子はルーティングにのみ使われ、
挨拶分類器とは意図的に共有されません — そちらでは `ハイ` が本当に `ハイ` のままで
なければならないからです。

editable install によってエージェントは*別の*コピーを import したために、すべての変更が
効果がないかのように見え、そして何も警告しませんでした。エージェントは正常に動いていました。

`start` と `gui` も起動時に同じヘッダーを表示します。現在のプロセスを超えて
`~/.ruder_ai/provenance.json` が、このマシンで観測されたすべてのチェックアウトと、

## Code Mode

RUDER-AI Code Mode は diverse な言語とフレームワークのソフトウェアエンジニアリング
タスクのために設計されています。

代表的なタスク:

* 既存コードベースの理解
* 関連ファイルの特定
* 実装変更の計画
* 新しいコードの記述
* 既存コードのパッチ
* プロジェクトコマンドの実行
* エラーの診断
* ビルドとテストの検証
* 変更のレビュー
* 失敗した実装試行からの復旧

本システムは、特定のエコシステムに限定されていません。

## 読み取り専用検査

`READ_ONLY_INSPECT` は非破壊モードです。

ユーザーの依頼にコーディング操作が含まれていても、この段階ではファイルを変更しては
なりません。

代わりに次を行うべきです:

1. プロジェクトを調査する
2. 依頼された変更を分析する
3. 関連ファイルとコードを特定する
4. 調査結果のみを返す

ファイル変更は、適切な Tool 権限を持つ段階に reserves されます。

## Web 検索による接地

`web_search` のような情報取得 Tool が使用された場合、その結果は応答の権威ある
情報源となります。

モデルは:

* 最終応答を検索結果に基づいて行うこと
* 矛盾する記憶情報を導入しないこと
* 結果に存在しない事実を作り出さないこと
* 検索結果が依頼された答えを含まない場合は、その事実を明示すること

これは、文書、バージョン、API、価格、日付など変化する情報に関する根拠のない主張を
減らすことを目的としています。

## 設計原則

### 決定論的実行

LLM の出力は、操作が発生した証拠として扱いません。

Tool の操作は実際に成功して実行された後でのみ、エージェントが完了を主張できます。

### 責務の分離

探索、計画、実装、テスト、レビュー、メモリはそれぞれ別の段階に分離されています。

### 独立した検証

実装を行う構成要素が、実装が成功したかを決定する唯一の構成要素であるべきでは
ありません。

### 明示的な認可

Tool 権限は、自然言語の指示だけに依存せずエグゼキューターが強制します。

### プロジェクト考慮

エージェントは、対象のエコシステムや規約を推測する前に実際のプロジェクトを調査します。

### 多言語サポート

同じ RUDER-AI コーディングアーキテクチャを、韓国語、中国語、英語、日本語専用の
モデル設定として公開できます。
